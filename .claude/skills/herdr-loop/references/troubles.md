# When something goes wrong

For the manager. Find the entry by what a script reported and read that one entry; none of this is needed while things go right. Commands are on the ops card.

## A worker

**Starting an attempt again.** The same three commands whenever a worker ends without a result (a pane that is gone, a usage limit, a hang): `hl-spawn close --id <ID> --phase <phase> --n <n>` (it answers "the pane was already gone" when that is so), `hl-items --run-dir <run> void --id <ID> --phase <phase> --note "<why>"`, then the same `hl-spawn start` line (for a review: `hl-serve stop`, then `hl-flow review` again). The attempt keeps its number and the new worker is a fresh session. What a builder had committed, pushed or opened is still there, and its brief tells the new builder to carry on from it. `void` is refused while the worker is open and once the attempt's result file exists (one exception, once for an item: "A review that does not count").

**A worker did not start** (`<phase> <n> of <ID> was not started and the attempt was given back`). The refusal ends with the pane's last lines, read before the pane was closed: read them first. A worker that printed an error and exited said there why; `timed out waiting for agent startup` by itself says only that Herdr waited. The attempt was given back, so the same start line works again once the cause is gone. The same words three times running are the machine or the kit and not the item: stop starting workers and tell the operator what the pane said.

**`blocked`: a dialog is waiting.** Read the pane's last lines (`herdr agent read <agent> --source recent-unwrapped --lines 40`). A permission prompt for the worker's own worktree or evidence directory: answer it. A question to a human: tell the worker nobody will answer and it must decide and record its decision (a short file in the item directory, sent with `hl-spawn prompt`). Anything else: do not answer it; start the attempt again. `hl-spawn` has already answered the folder-trust dialog; never send a bare `enter` to an agent that is starting.

**`stopped`: not working, no progress for three minutes, no done file, and no command of its own still running.** Read the pane's last lines. A Cursor question box: `herdr agent send-keys <agent> esc`, then tell it nobody will answer. A turn that ended early: tell it once to continue from where it stopped and to finish with the done file. If one nudge does nothing, start the attempt again.

**`quiet`: no progress for ten minutes while it reads as working, or while a command of its own is still running** (`command_running` in the event). A long test run on a busy machine is quiet for good reason; read the pane's last lines, and wait again unless it has truly hung: waiting again will not wake you for the same silence. Hung mid-turn: start the attempt again.

**`gone`: Herdr no longer has the agent.** Start the attempt again.

**`limit`: a Claude worker's last reply is a usage-limit refusal**, with `resets_at` and `seat`, the sign-in it hit. That record in the worker's own transcript is the only thing that counts as a limit. Text on a screen is not proof: a warning at 75 % of a window is not a block, and treating one as a block once parked a loop for 58 hours. Close the worker and void the attempt. Then look at `seat` in `hl-seat --root <root> status`: when the program is on another seat now, it moved after this worker started, so start the attempt again at once and the new worker comes up on the open seat. When it is the program's seat, start nothing on Claude: within five minutes the watchdog places the program on a seat with room, or pauses it, and `hl-wait` tells you with `seat` (next section). Meanwhile send builds to Cursor where the item allows it. A Cursor worker has no such record: for Cursor a block means no progress after one nudge and a reset time on the screen. If your own seat is limited you will simply stop; the watchdog starts a fresh session on an open seat, or after the reset when none is open.

**`error`: Herdr or `gh` failed five looks in a row.** Read `detail`. GitHub or its runners being down is the next entry but one.

**`prompt_sent: false`, or "did not take the prompt".** Three tries did not get the one line taken. Read the pane before anything else; never send a brief a second time blind.

**A malformed result file.** The author fixes its own file, once, if it is still open. You never edit a result file. A verdict `hl-flow reviewed` lists problems for is not a usable verdict: a fresh reviewer runs.

**A reviewer hangs in a browser call** (its transcript shows one tool call open for more than ten minutes), or **its browser will not start** (the verdict comes back `INCONCLUSIVE` with the tool's own words). The first: start the attempt again. The second is the machine, not the build: run the browser install line in `host-facts.md` (the Playwright row), then review again with a fresh reviewer. It counts as a review.

## The program's Claude seat

**`seat`: the program has moved to another Claude seat, or is paused.** `hl-wait` reports it on every wait while it holds, and the answers of `hl-flow save` and `hl-claim beat` carry it too, so a long turn sees it at its next save. The watchdog decides it from the seats' readings (`hl-seat --root <root> status` shows them and why). You never move, pause or resume the program yourself, and never edit `seat.json` or `program.json` for it.

- **`action: move`** (`from`, `to`). The seat you run on is full, and the program is on `to` now: every Claude session started from here on comes up there. Hand over at once, between steps (a merge in flight finishes first): stop every background command of yours by its PID, write "Now", `hl-flow save`, `hl-claim --root <root> release --note "seat move to <account>"`, say in one line that you are handing over, and stop. Workers at work keep running on the old seat until they end; one that stops on a limit there is started again by the next manager (`limit`). The watchdog starts the next manager on `to` within five minutes, and a seat hand-over never counts as an idle one.
- **`action: pause`** (`until`). Every seat is full. Let a running `hl-merge` finish. Close each Claude worker and void its attempt with `--note "seat pause"`, and `hl-serve stop` for a review that was running. Leave Cursor workers running: they use neither seat, and the next manager reads their results. Write "Now" as the point to resume from, with `until`; `hl-flow save`; `hl-claim --root <root> release --note "seat pause until <until>"`; stop. Never disarm the watchdog: it starts nothing while the pause holds and starts a fresh manager on the first seat to reset. The operator was told by the watchdog; tell them nothing more.

## Checks and GitHub

**Required checks are red.** `hl-wait --checks` and `hl-flow review` write the failed checks to `checks-<build>.md` in the item directory. That is a rework: start the next build and its brief points at the file. A known flake or an outage instead: re-run it once (`hl-items start --id <ID> --phase ci_rerun`, then `hl-secrets --root <root> run -- gh run rerun <id>`); a green re-run removes the file. A second failure is real. A build that passed its review and is red here may have worked in its worktree only because of a file that is not committed: one git ignores, or an untracked one that appeared after `hl-flow built`. The check of a review's checkout sees neither (`design.md`, "What the check of a checkout does not see").

**A review that does not count.** `hl-flow reviewed` answers with `problems`, or `hl-merge` refuses with `review <n> does not count for a merge: …` or `review <n> has not been read`. Not read: run `hl-flow reviewed --id <ID>`. With `checkout` among the problems, the review passed over a checkout that moved, or in which a tracked file changed, while it ran: that pass never was a pass of the head. `next` in the answer, and the refusal, say what to do, with the command. The first time for an item, give the attempt back: `hl-items --run-dir <run> void --id <ID> --phase grade --n <n> --note "<what changed the checkout>"`, then `hl-flow review --id <ID>`. It does not use up one of the build's reviews, and `hl-flow review` refusing with `grade bound reached` names the same command when it applies. An item gets one give-back (`give_back` in the run's bounds); the second time `void` is refused, and the next entry says what then. The review stays in the attempt log, marked. A delta confirm that was given back was still the item's one confirm, so the review after it is a full one.

Only a pass is given back. A fail or an inconclusive over a changed checkout stands as what it is: `checkout` is in the answer, nothing for it is under `problems`, and the build goes back, or the criterion is corrected, as after any other. What `reviewed` saw of the checkout the first time is kept on the attempt and stands: a file edited and then put back looks untouched later, and nothing reads it again. Any other problem (a verdict that is unusable, a review that exercised nothing): start a new review with `hl-flow review --id <ID>`. That one stays counted, and past the bound the item is parked like any other.

**A tracked file changes during every review.** `void` refuses with `give_back bound reached`, and `hl-merge` and `next` say to park the item: a second pass of this item was read over a changed checkout. That is not a reviewer's doing. A test run, an install or the served build rewrites a file the repository tracks (a lockfile, generated code, `next-env.d.ts`) after the reviewer has started, or the build writes one as it is stopped, which no reviewer can put back. No command lifts that at the merge. The cure is in the repository: take the file out of what git tracks (`git rm --cached <path>`) and ignore it. Park the item with the command the refusal names (`environment`), tell the operator which file and what rewrites it, and write that change as an item of its own, ahead of the rest. A file rewritten before the reviewer starts is another matter: the entry on `written-before-review`, below.

**`hl-flow review` refuses: the checkout is not the commit under review.** Tracked files in the item's worktree differ from its commit before anything is served: what a review that was given back left there, or a hand. A review is of what is committed, so none was started and none is spent. Run the command the refusal names (`git -C <worktree> reset --hard HEAD`; it leaves untracked files alone), then `hl-flow review` again. Where it says the checkout is at another commit, there are two causes, and it names the command for the one it found. A reviewer switched it, to compare as a rule: `git checkout -B` puts it back on the item's branch at the commit under review. Or the branch has gone on since the build was accepted (you merged the base in for `hl-merge` exit 4, or a commit was pushed): `hl-flow built --id <ID>` takes the new head up, and the review is of that. Where it names a submodule command, a submodule's own files were changed. Where it says git was told not to look at a file, the file is marked assume-unchanged or skip-worktree (`git update-index`, or a sparse checkout, which a loop's worktree may not be), which hides it from `git status`: the refusal then names three more commands to run first. A change that ought to be part of the item is a rework for its builder, never something to review from the worktree. Putting the files back changes nothing an earlier review's read found: that is on its attempt.

**`hl-flow review` answers `written-before-review`** (exit 4). Once the build was served, tracked files differed from its commit: its own Serve or Ready line wrote them, or the setup run again. The reviewer would be given a build that is not the commit, so nothing was started and no review is spent. It is the build's fault and a rework: start the next build (manager prompt, step 4); the script has written the files, and what to do about each, into `rework-<n>.md`, which that build's brief points at. If they are paths the repository rewrites by itself and that is harmless (a lockfile an install touches, `next-env.d.ts`), that is the operator's to say: the spec's `rewrites` for the repository, then staging again. The run takes it up as it is, because a repository's facts are read from `program.json` every time. A path named there is only noted (`dirty_before` in the answer of `reviewed`).

**The checkout could not be read when the review was over** (`checkout` in the answer of `reviewed` says so). The item's worktree was not there, or git could not read it. That goes on the review's attempt for good, as a checkout that changed: made again later, it would read clean. A pass is given back like any other pass over a changed checkout, once for an item; a fail stands. `hl-flow review` then refuses while the checkout cannot be read, and names `hl-flow prepare --id <ID>`, which makes it again from the item's branch.

**`hl-spawn start` or `hl-flow review` refuses: the brief does not begin with the brief this script renders.** A file was already at the brief's place, and it is not what the script renders now with something added below. Either something else wrote it (a builder can write the item directory), or it was rendered for a state that has changed; a review's brief rendered before the build was served never matches, because it says what the served build answered. Remove the file and run the command again. `brief_notes` in the answer of a start counts the lines that lay below the script's own brief and went with it: if you added none and it is not 0, something else did; close the worker and read the file. To give a reviewer a note, write it to a file and pass `--note-file <file>` to `hl-flow review`: it goes into the review brief's own slot.

**A command refuses: `contract.md` is not the contract that was installed.** Something wrote the file; a contract is changed only by `hl-items contract`. `hl-items --run-dir <run> contract --id <ID> --restore` writes the installed text back. If that refuses too, what it was installed from was written as well: tell the operator.

**`hl-merge` refuses: `verdict-<n>.json` is not the verdict `hl-flow reviewed` read.** Something rewrote or removed the file after the review was read. Nothing of the loop does that, so tell the operator. The head is reviewed again (`hl-flow review --id <ID>`, with `--full` after a confirm); that is one more review of the build.

**A command refuses: `attempts.json` is missing.** The record of the item's attempts is gone and no command makes it again. Leave the item as it is and tell the operator.

**`hl-flow built` sends a rework back for a file its builder did not touch** (`the worktree is not clean: <path>`). Something rewrote a tracked file the spec names under `rewrites` while the build was served for the review before; that review's answer had it under `dirty_before`, and its reviewer left it as its brief says. The builder's fix file names the command that puts it back (`git checkout HEAD -- <path>`). Only this check, when a build is accepted, asks for a clean worktree. `hl-merge` does not look at the worktree: a pass with such a file merges, and `hl-flow close` removes the worktree with it.

**`hl-flow built` sends a build back: git was told not to look at tracked files.** The builder marked a file assume-unchanged or skip-worktree, so `git status` says nothing of it whatever it holds. The reason in the builder's fix file names the commands that clear the marks; the file is then committed or put back.

**A delta confirm.** `hl-merge` refuses with `review <n> is a delta confirm that cannot stand in for a full review: …`, or names the review before it, a second confirm, or the program's settings. Something changed after the confirm started (the base took the branch in, the failed review's record or the contract changed), or the confirm is on record without the script having given it. The reason is in the refusal. `hl-flow review --id <ID> --full` reviews the same head in full; it counts as one more review of that build. `hl-flow review` refusing with `was rendered as a delta confirm's brief`: a brief you rendered beforehand is for a confirm the script no longer gives. Remove the file it names and run it again.

**GitHub or its runners are down.** Jobs with no runner and zero steps are an outage, not a build defect. Stop starting items, wait, re-run what was cancelled, and void what was lost.

**`hl-merge` exit 4: the base moved and the branch is behind.** Merge `origin/<base>` into the branch in the worktree (never rebase or force-push), push, wait for the checks, run `hl-merge` again; it accepts the new head only if the patch is unchanged. If the merge conflicts, that is a rework with your reason in `rework-<n>.md`, and a new review.

**`hl-merge` exit 3: the lock is held**, possibly by LoopRunner for up to 40 minutes. Wait and run it again.

**A required check never reports.** `hl-wait --checks` answers `passed: false` with `not_reported: [<names>]` once the grace has passed, and `hl-merge` refuses with `required checks are not green: <name>=pending`. The base branch requires the check (its protection or a ruleset) and this pull request has not started it. Why it never started decides what is next. Actions was down, or the run was lost, when the branch was pushed: a new push starts it. Push an empty commit from the item's worktree, wait for the checks, and run `hl-merge` again; it accepts the new head because the patch is unchanged. The check's workflow leaves this change out (a path or a branch filter): the repository's protection asks for what cannot happen in this loop. That is the operator's: park the item (`ci`) and ask once.

**GitHub says blocked.** `hl-merge` refuses with `GitHub reports the pull request blocked (merge state BLOCKED) although every required check it lists is green`, or `although it lists no required check`. GitHub will not merge the pull request, and nothing it lists for it is red. `hl-merge` has already asked GitHub again, four times over fifteen seconds, so this is not GitHub being a moment behind checks that just turned green. Every check the base branch requires is in the list (one that has not reported reads `pending`, above), so the branch requires something else that has not happened: an approving review, resolved conversations, signed commits, a deployment, or a required check reported by another app than the one the rule names. Nothing here gives those. That is the operator's: park the item (`ci`) and ask once.

**`hl-merge` refuses for an earlier item's Verify.** An item of this run merged and its deploy check has not passed. Run `hl-verify` for it; nothing else of the run merges until it has.

**A pull request merged without `hl-merge` finishing** (your merge was interrupted, or something else merged it). Run `hl-merge` again. It records a merge of the reviewed commit and refuses any other; on that refusal the item is `failed` with `operator: merged outside the gate`, and the operator hears of it at once.

**A commit carries a `Co-authored-by` line naming a tool.** Cursor adds one by itself. The clone's hook refuses such a commit, `hl-flow built` sends the build back for it, and `hl-merge` refuses it again. The fix is the builder's: rewrite its own branch's commits without the line and push with `--force-with-lease`. The patch is unchanged, so a review already given still stands.

## A train

**`hl-train promote` answers `red`.** A required check of the batch failed; nothing reached the base and the batch is still open. Read the failed run (`links` in the answer). Jobs with no runner and no steps, a cancelled run, or a check that says it is being retried are not the batch's fault: re-run it once and `promote` again. A failure in its own right: `hl-train … repair` closes the batch and writes `batch-<n>-red.md` (what failed, and what the batch holds) and `repair-<n>-ITEMS.md`, a one-item backlog. Run it in a run of its own (the command is in the answer), then `test` again. The items of the red batch stay merged in the train and go out with the batch that is green. Whether other items go on merging meanwhile is your call (manager prompt, "A repository with a train").

**`hl-train promote` refuses: GitHub reports the batch's pull request blocked.** Every required check GitHub lists for the batch is green, or it lists none, and it still will not merge it: "GitHub says blocked", under "Checks and GitHub", says how to find what is missing; `promote` has asked GitHub again the same way before saying so. The batch stays open and nothing is promoted meanwhile. A batch's branch is never pushed to, so where a new push would start the missing check, `hl-train … abandon --note "<why>"` and `test` again: the new batch's pull request starts the workflows afresh. Blocked the same way a second time, it is the operator's.

**`hl-merge` refuses: the train is at its limit.** Too much has merged since the last promotion to go on untested. `hl-train status` says what is open: a batch to promote, a red one to repair, or no batch at all, in which case `test`.

**`hl-train` refuses: a commit on the train that this loop did not merge.** Something pushed to the train's branch, or a pull request was merged into it without `hl-merge`. Nothing is tested or promoted with it there. Read the commit. A merge of an item's pull request made outside `hl-merge`: run `hl-merge` for that item, which records it if the reviewed commit is what landed. Anything else is the operator's: say so at once.

**`hl-train test` refuses: merged by the records and not on the train.** The train's branch was rewritten. Do not recreate it: tell the operator.

**A check a repository names for an item never reports** (`not_reported` from `hl-wait --checks`). The spec's `item_checks` names a check that pull requests into the train do not start, usually because its workflow runs only for pull requests into the base or only when certain paths change. That is the spec's fault and not the build's. Look at the pull request's checks to be sure it never started, then `hl-items --run-dir <run> drop-item-check --name <check> --note "<what you saw>"` for each run it holds up, and tell the operator so the spec is corrected for the next program. The batch still runs every required check before anything reaches the base.

**`hl-train` refuses: another command is at work on this repository.** One of `test`, `promote`, `repair`, `abandon` is still running for it (a `promote` can wait a long time for the merge lock). Wait for it; do not start a second.

**`hl-train` refuses: a batch is merged into the base and its records are not finished.** A `promote` was cut short after GitHub merged. Run `promote` again: it only finishes the records.

**`hl-train test` refuses: on the base already, and no promotion on record put them there.** Something other than this loop merged the train, or an item's branch, into the base. Tell the operator; do not mark anything by hand.

**A Verify answers `not-promoted`.** The item's merge is still on the train. It runs after `hl-train promote`.

## The ledger

**`hl-flow archive` refuses.** Read which refusal it is:
- `an archive moves only what a sweep has read`: the move was asked without `--swept`. Run the dry run with `--out`, have it read (the manager prompt, "Keeping the ledger short"), then `archive --swept <that file>`.
- `… is not a file hl-flow archive --dry-run --out wrote`: `--swept` names another file, a sub-agent's findings perhaps. Give it the dry run's own file.
- `the sweep file could not be written`: the folder of `--out` is not there. Make it (`mkdir -p`) and run the dry run again.
- `nothing was archived: the ledger changed while the archive was being worked out`: a save, or a sub-agent's edit, wrote the ledger at the same moment. Nothing was written over. Run `archive --swept` again with the same file.
- `nothing was archived: the ledger would change beyond the rows that move`, `the rows of the ledger and its archive would differ after the move`, or `did not read back as written`: the script would have lost or doubled a line, and every file is as it was. A table it reads differently from the way it was written is the likely cause: a second `## Decisions` or `## Gates` heading, a hand edit of `LEDGER-ARCHIVE.md`. Do not edit the archive or move rows by hand to get past it. Tell the operator with the answer whole, write a line in "Now", and go on: the archive is about size, and nothing waits on it.
- `nothing was archived: …` naming a file that could not be written, or `FOLLOW-UPS-ARCHIVED.json` that could not be read (and a dry run's `what would move could not be worked out`): every file written was put back as it was. A full disk is the machine (below). A JSON file that does not read was written by something other than the script: tell the operator, and leave it as it is.
- `the archive failed and could not be undone whole`: a write failed, and a file already written could not be put back, or had been written since by another writer, whose work putting it back would lose. The answer names it and the files written before it, all left as they are. Every row is still in the ledger or its archive, and some may be in both. Archive nothing more, write it in "Now", and tell the operator with the answer whole.
- An answer with `broken` is not a refusal: those rows stayed where they are. `decisions` (by number) and `gates` (by name) are rows broken over two lines, a line of text under a row or a row with an empty first cell written under the row it adds to: mend each into one line (a Decision's text is yours). `unclear_gates` are gates whose last row reads more than one way, because a `|` sits in its Gate, Before or Result cell (inside code or written `\|` too) or a backtick is left open, or that has fewer than three cells: close the backtick, say what the cell says without the pipe (a command can go under How it was checked, after the Result), or give the row its cells with the Result third. Such a gate is never taken as settled, here or by `clocks`. The next archive takes them.
- `this program is not claimed by pid …`: another manager holds the program. Stop, touching nothing, as for a refused save.

## The machine

**The host's Docker runtime is stuck** (`docker` does not answer or hangs, containers fail with I/O errors, or the kernel log of the runtime's Linux VM shows disk errors). This is the machine, not an item: nothing is failed, parked or reworked for it, and any loop's manager fixes it (the operator, 2026-11-02). The runtime's own commands are the host's, so a program that needs Docker names them in its spec (a repository's `facts`). First start the runtime if Docker does not answer; a start does nothing to one that is up. Still broken: when `docker ps` answers and lists another program's container, wait for that program rather than restart under it. Otherwise restart the runtime. Then read `docker ps`, `docker run --rm alpine:3 true` and the last 50 lines of `dmesg` inside the VM (no new I/O errors), and write what was wrong, what you ran and those three readings in the ledger. Never stop the runtime or delete its VM or disk: other programs' tests use it, and whatever keeps it running on the host is not the manager's to change.

**A port is taken.** `hl-serve start` (inside `hl-flow review`) refuses and names the process. Read its full command line. A leftover of this program's own item (its serve record says so): stop it with `hl-serve stop` for that item. Anything else: do not touch it; report it and park the item.

**`hl-flow prepare` answers `setup-failed`.** The repository's setup command did not succeed in the worktree, or left files git does not ignore; its last lines and its log are in the answer. A network or registry outage: run `prepare` again. Otherwise the worktree is not ready and its brief will not say it is: the builder installs for itself, and the program's spec needs its `setup` corrected between items.

**A secret cannot be read.** A script refuses with ``the reader did not give `<name>` (<ref>): …`` or `the program's keeper did not give the loop's token`, or `hl-spawn start` refuses with `the worker's secrets did not load (hl-env FAILED …: no … token …: …)`. The words after the last colon are the first line the secrets reader printed on stderr (`hl-read-secret: …`, or the program's `secrets_reader`). This is the environment and never an item's fault: `hl-spawn` has given the attempt back, and no item is failed, parked or reworked for it. `hl-secrets --root <root> status` shows which secret failed and how long ago. Where the program reads through a 1Password service account, `hl-secrets --root <root> budget` shows what the account has left, and words like "rate-limited" or "too many requests" mean the day's limit is used up, by this program or by anything else on the host that reads through that account; elsewhere `budget` answers `"applies": false`, and its `hold` still says whether the keeper's last read failed. `account_remaining` at 0 by itself means nothing while reads work: `budget` says under `hold` whether to stop, and it says so only when a read failed, or when the counter is low. A secret the keeper already holds is not what failed: it stays in use past its lifetime until a read succeeds, and `status` lists it with `past_lifetime_since` and `last_error`; that needs nothing from you beyond telling the operator once. What fails is a secret that was never read, which is the case after a keeper started anew. While that lasts: start no worker and no new item that needs it, and let what is running finish (a worker keeps the tokens it was started with). Do not try to read around it: no `hl-read-secret` by hand, and no `hl-secrets forget` or `stop` to make the keeper ask again. Every try is a request, a failed one may still be counted, and `forget` and `stop` drop the secrets the keeper still holds, which are what the program is going on with. Tell the operator once: `hl-secrets notify` works while `status` lists `ntfy` under `held`; when it does not, your reply and the ledger's "Now" are the only channel. For a rate limit, it is over when `budget` shows requests left again (`reset` says when the limit resets). The keeper reads again by itself at the first request that comes ten minutes or more after a failed read, so the same command then works. Other words (an item or a file not found, a vault the account cannot see, a file whose permissions `hl-read-secret` refuses) mean a reference in `program.json` is wrong or a secret was moved, renamed or exposed: that is the operator's, so park what needs it and ask once. After a secret was rotated, `hl-secrets forget`.

**`no keeper is running`, `a keeper could not start`, or `none answered`.** Nothing was asked of the secrets store. `<root>/secrets.log` says why in its last lines. `another keeper (pid <n>) holds …`: a keeper is alive and its socket is gone. Read that one PID's command line (`ps -o command= -p <n>`); if it is this root's `hl-secrets … serve`, kill that PID and run your command again. **`the keeper … did not answer`, or `went without answering a request`:** a keeper was there and may have asked the secrets store, so no script asks again by itself. Run the command again, once. If it says the same, `hl-secrets status` names the keeper's PID under `last_pid`: read its command line and kill that one PID as above.

**`the program's Claude sign-in did not load`, or a Claude worker `running without CLAUDE_CONFIG_DIR`.** The program runs its sessions on the sign-in of the seat it is on (`hl-seat --root <root> status`, `seat`: one of `claude_config_dir` and `claude_seats`), and that directory holds none now (`hl-home FAILED … no Claude sign-in`), or the pane did not take it. `hl-spawn` gave the attempt back; nothing is failed, parked or reworked for it. A missing sign-in is the operator's (their login): start no Claude worker, let what is running finish, and tell the operator once that `CLAUDE_CONFIG_DIR=<that directory> claude` needs `/login`. Never edit `program.json` or `seat.json` to another directory or account to get going: the operator chooses the accounts, and only the watchdog moves the program between them. A pane that did not take it (no `hl-home` line at all) is the host's: start again once.

**A Verify failed** (`hl-verify` exit 4). The manager prompt's step 9 says what a red deploy means. Read `verify-<n>.txt` first: a Verify that could not run (a missing tool, a command that reads a branch that has moved on, `base_moved` in the answer) is not a red deploy. Nor is one whose own line is wrong: it can never pass, whatever the deploy did (it reads a log that prints differently than the line expects, say). Confirm the deploy by reading it yourself, record what you read, and ask the operator once to correct the line: backlog files are theirs. Once it is corrected and staged (staging names it under `verify_lines_to_load`), `hl-items --run-dir <run> verify-line --id <ID> --note "<what was wrong>"` loads it, and `hl-verify … --retry --note "Verify line corrected"` runs it. `verify-line` refuses a Verify that has passed, one that is running, and a file that differs from the run anywhere but in Verify lines. Never edit `item.json` for it.

**You are unsure whether something is yours to do.** Repository settings, branch protection, secrets, DNS and anything in another repository are not an item's work. If the program needs one and you hold the means, do it as the manager, record it in the ledger under Gates, and say so in your report. If it needs the operator's identity, park and ask once.
