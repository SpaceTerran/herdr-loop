# Host facts: what a loop host needs, and what was measured on one

For whoever changes the kit or sets a program up. A manager does not need this file to run a program; what it needs is on the ops card.

The kit was built for, and measured on, the author's always-on Mac mini, reached from a laptop over SSH as `<you>@<loop-host>`. The first section says what any loop host needs. The rest is what was learned on that mini, kept because it explains why the scripts do what they do. Every fact carries how it was learned: "SSH" is a read over SSH on 2026-10-11, "spike" is the Phase 0 run inside Herdr on the mini the same day (`phase0-spike.md` is the procedure), and later dates are named.

## What a loop host needs

- **An always-on Mac.** The watchdog is a LaunchAgent, and closing a worker reads macOS process facts (`hl/reap.py`). Nothing has been run on another system.
- **Herdr**, with its server kept running (the author's host keeps it up with a LaunchAgent of its own).
- **Claude Code**, signed in on at least one seat that is not the host's default sign-in (Claude sign-ins, below), with Herdr's hook installed (`herdr integration install claude`) and the seat recorder in the shared `statusline.sh` (below).
- **The Cursor CLI** (`agent`), signed in once on the host, if any item is to be built by Cursor.
- `git`, `gh`, `jq`, `python3` (`/usr/bin/python3` 3.9 is enough), and `node` with `npx` for the evaluator's browser.
- **A way to read secrets**: `scripts/hl-read-secret` (below) with references it can resolve on the host, or a reader of your own named in `program.json`'s `secrets_reader`.
- **A loop root per program** (`/Users/<you>/loops/<program>`) that nothing else syncs, reverts or cleans: the ledger clone, the stream clones and every run directory live there.
- **Memory to spare.** The manager starts nothing while less than 20 % of memory is free (Capacity, below).

| Reading a secret | `scripts/hl-read-secret <ref>` writes the secret to stdout with no trailing newline and nothing else, or one line on stderr and exit 1; the value goes nowhere else. `file:<path>` (a leading `~/` is the home directory) is the file's content less one trailing newline, and is refused unless the file is the user's own with no group or other permission bits; it works everywhere (over SSH, in panes, under launchd), so it is the default. `op://…` is `op read` with whatever sign-in `op` has. `keychain:<service>` is the login keychain's generic password for that service; it works in Herdr panes and LaunchAgents but not over SSH, so not in `stage.sh`, and `security` prints a password holding non-printable bytes as hex. `env:<NAME>` is that variable, never `GH_TOKEN`, `GITHUB_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY` (a worker's pane clears those before it reads). An unknown scheme or an empty value is refused. A program whose secrets live elsewhere names its own reader in `program.json`'s `secrets_reader`, a command as a list of words with the reference appended; the keeper and the watchdog use it (a worker's pane in a program without the keeper always reads with `hl-read-secret`), and its first non-blank stderr line is what a failed read reports. `stage.sh`, piped over SSH, finds the reader at `HL_READ_SECRET`, beside itself, or on `PATH` (`~/.local/bin` first), so copy it to `~/.local/bin` on a new host | the kit |
| One 1Password service account's daily limit | The author's secrets were first read through a 1Password service account, which allows 1,000 requests a day for the whole account, shared by everything on the host that reads a secret. The first real program made about 100 an hour: its manager about 40, reading the GitHub token on almost every shell call, and every worker two in its pane. It reached the limit after ten hours, and for the next fifteen nothing that needs a secret worked. A failed read may still count. That is why the keeper exists. `op service-account ratelimit` prints the counters and no secret, and on that host had to be run as `env -i OP_SERVICE_ACCOUNT_TOKEN="$OP_SERVICE_ACCOUNT_TOKEN" HOME="$(mktemp -d)" PATH=/opt/homebrew/bin:/usr/bin:/bin op service-account ratelimit < /dev/null`; `hl-secrets budget` runs it so, without putting the token on a command line. | Secrets keeper | `hl-secrets`: one process per loop root, started by the first script that needs a secret, in a session of its own. Never run `agent login`, `agent logout`, `agent --api-key …` or set `CURSOR_API_KEY` on a loop host: one login replaces the account for every running agent.

A loop host may run other things: on the author's mini, older loops and an assistant bot ran beside the programs. The kit touches only the Herdr workspaces, tabs and panes it opened, its own loop roots and its own LaunchAgents. Whoever sets a program up does the same.

**The seat recorder.** These lines follow `input=$(cat)` in `~/.claude/statusline.sh`, which every sign-in on the host shares by link. They never fail the line: a payload without `rate_limits` or `session_id` writes nothing.

```bash
# Herdr loop seats: record this session's reading of its sign-in's usage windows, one file
# per session, for hl-seat (herdr-loop references/host-facts.md, "Seat readings"). Never fails the render.
_hl_dir=${CLAUDE_CONFIG_DIR:-$HOME/.claude}/hl-usage
_hl_sid=$(printf '%s' "$input" | jq -r '(.session_id // "") | gsub("[^A-Za-z0-9-]"; "")' 2>/dev/null)
if [ -n "$_hl_sid" ] && _hl_rl=$(printf '%s' "$input" | jq -ce 'select(.rate_limits != null) | {observed_at: (now | floor), rate_limits}' 2>/dev/null) && mkdir -p "$_hl_dir" 2>/dev/null; then
  printf '%s\n' "$_hl_rl" > "$_hl_dir/.$_hl_sid.$$" 2>/dev/null && mv -f "$_hl_dir/.$_hl_sid.$$" "$_hl_dir/$_hl_sid.json" 2>/dev/null
fi
```

## What a worker is, as measured

**A Claude worker** started with the flags `hl-spawn` uses has exactly its role's tools plus `EndConversation`, no MCP server except an evaluator's browser, no slash commands (so `/exit` does not exist), no hooks, plugins, skills or memory, and `permissionMode: bypassPermissions`. In the spike, run in the loop root, the one instruction file it loaded was the root's `CLAUDE.md`. Read from the `prompt_snapshot` attachment of its transcript; an interactive transcript has no init record. (spike)

- Its own token is in the agent process and is withheld from the commands it runs: inside a worker `CLAUDE_CODE_OAUTH_TOKEN` is empty and `GH_TOKEN` is set. `hl-spawn` checks the agent process, not the worker's word. Where `worker_claude_ref` is `-` a Claude worker has no Claude token, and `hl-spawn` checks `GH_TOKEN` only.
- In a directory Claude has not trusted it stops on "Is this a project you created or one you trust?" whatever flags it was given, and the default answer is "No, exit". `hl-spawn` answers yes by moving to that line. Never send a bare `enter` to a starting agent. Trust is inherited from a parent directory: in the canary, once the loop root was trusted, workers started in new directories under it with no dialog. So the dialog is met by the first session in a new loop root, which is the program's first manager.
- Herdr calls an agent `idle` and `interactive_ready` the moment that dialog is answered, while Claude is still starting and has drawn nothing. What is typed before its input box is there is lost: the text, the Enter, or both. The first manager of the first real program sat with its prompt typed and unsent until Enter was pressed by hand (2026-10-12), and sending at once reproduced it in 4 first starts of 6, then 4 of 8. After the dialog the scripts wait until the screen shows the input box (a rule with a line under it that starts with `❯`); with that wait, 6 of 6 were taken.
- `herdr agent prompt` answers ok for text that went nowhere. With `--wait` it answers `agent_prompt_stalled` when it sees no work begin within 5 seconds. Typed text whose Enter was lost is started by `herdr agent send-keys <agent> enter`; in that state the first Enter was not taken and the second was, both times it was seen. Enter on an input box that holds nothing does nothing. (mini, 2026-10-12)
- This Claude Code refuses a bare foreground `sleep` and turns it into a background task, after which the turn ends and Herdr reads `done` while the task still runs. Briefs never ask a worker to wait on a timer.
- A prompt under about 600 characters arrives as typed. Over about 950 it arrives wrapped as pasted content, which a session is told may hold instructions its user did not write. Every prompt the scripts send is one short line pointing at a file.

**A Cursor worker** is started with the operator's flags and is not isolated: it loads the MCP servers of the Claude plugins in `~/.claude/plugins`, runs the hooks in `~/.cursor/hooks.json`, and had 7 % of its context used after one trivial prompt. `--approve-mcps` therefore approves more than a project's own `.cursor/mcp.json`. This is the operator's decision on record. (spike)

- It adds a `Co-authored-by: Cursor` trailer to its commits on the command line although both attribution settings are `false`. Three things stop that reaching a base branch: the build brief forbids it, the clone's `commit-msg` hook refuses the commit, and `hl-merge` reads every commit on the pull request.

**Herdr's reading of an agent is a hint.** (spike)

| Reading | Claude | Cursor |
|---|---|---|
| `working` | reliable during a foreground command | reliable |
| `done` | also shown while a background task of its own still runs; it then speaks again by itself | also shown while it waits on a question box |
| `blocked` | reliable for the trust dialog | not raised for a question box |
| `idle` | shown only after someone has viewed the tab | same |

The done file is the signal. `hl-wait` judges progress from a Claude worker's transcript and from how long a Cursor worker has not been working.

**Closing a pane ends everything in it**: the agent, its MCP servers, a browser's nine processes, a served build started in either shape (`exec` or `&` with `wait`). Closing a tab's last pane removes the tab, and closing a workspace's last pane removes the workspace. (spike, five cases; probe 2026-10-11)

**Closing a pane does not end what a worker's shell commands left in the background.** Claude Code runs each Bash command in a zsh it starts in a session of its own (no terminal; the shell's pid is its session and its process group). A job the command put in the background keeps that session when the shell exits, and launchd adopts it; neither the pane shell's session nor any process group the pane knows holds it. On macOS `ps -o sess` prints 0 and `pgrep` has no `-s`; `os.getsid` reads any process's session. macOS hides the environment of its own programs (`/bin/zsh`, `/bin/sleep`) from other processes, so a variable set for the worker finds a `node` or a `python` and never a shell loop. So `hl-spawn` has every shell of a worker write itself down through `ZDOTDIR`, and `hl-spawn close` kills what is still in those sessions (`hl/reap.py`). A builder's four CPU loops ran nine and a half hours before that, on the help-desk catalog program. (mini, 2026-11-02, Claude Code 2.1.316: two `sleep`s left by a Bash call had parent 1 and the dead tool shell's session, not the pane's)

**Not every Herdr command prints a reply.** `pane run` and `pane send-keys` exit 0 and print nothing; `pane close` prints `{"type":"ok"}`; the rest print a JSON object. The exit status is what says a command worked. A pane, agent or workspace that is not there answers `pane_not_found`, `agent_not_found`, `workspace_not_found` with exit 1. (probe 2026-10-11, after the canary's first spawn stopped on this)

## Capacity, as measured

Measured on 2026-10-11 (spike, on the M2 mini): 41 % free and swap 2.46 of 3.0 GB used with no worker; 39 % with one idle Claude and one idle Cursor worker; 33 % with those two plus an evaluator and its browser. A Claude worker is about 270 MB after a turn; a Cursor worker 570 MB at start and 95 MB idle; an evaluator's browser 630 MB across nine processes. By these figures two streams fit side by side: a second stream at its heaviest (an evaluator and its browser, about 900 MB) on top of the 33 % case leaves roughly a quarter of memory free. A third stream has not been measured. The number of streams is not a setting: before each spawn, the 20 % line decides.

## Starting a program's first manager

```
<kit>/scripts/hl-watchdog --root <root> --herdr <path> start --note "<why>"   # from outside Herdr, by whoever sets the program up
<kit>/scripts/install-watchdog.sh <root>                                      # once per program: a LaunchAgent, every 5 minutes, starts disarmed
```

`start` opens the manager's workspace (labeled with the program's name), starts the manager there with the launch line at the top of the manager prompt, answers the folder-trust dialog, waits for the session's input box, and sends the one line that points at `MANAGER-PROMPT.md`, seeing that it is taken. A session that does not take it is closed and the start refused ("was started and did not take its prompt"); run `start` again. It refuses while a live manager holds the program. Before anything is pinned it needs `--herdr <path>`; afterwards it uses the pinned file. A replacement manager opens as another tab of the workspace the last one ran in.

The watchdog's LaunchAgent is labeled `${HL_LAUNCHD_PREFIX:-local.herdr-loop}.watchdog.<slug>`, the slug being the program's name; set `HL_LAUNCHD_PREFIX` when installing it to put it under a prefix of your own, and set it the same for `install-watchdog.sh --remove`.

## What round 2 measured (2026-10-12, Claude Code 2.1.296)

- A manager started with the operator's bare launch line begins every request with about 50k tokens: 31k of tool definitions (one tool alone is 13k), 8k of skill listings, 5k of MCP names and instructions. With `--tools "Bash,Read,Edit,Write,Agent,TaskStop" --disable-slash-commands --strict-mcp-config --mcp-config mcp-none.json` a session on the laptop began at 9k. `--tools` alone made it worse (88k): without the tool search, every MCP tool is loaded in full. The three go together. (laptop; the mini is to be measured when it is free)
- `--tools "…,Agent"` opens the sub-agent tool to a worker; the session lists it as `Task` and calls it `Agent`. `--agents <file>` adds the kit's types.
- A sub-agent call that names no `run_in_background` is launched in the background: the turn can end before it returns, and the session is invoked again when it does. A `model` on the call overrides the agent's own, and `CLAUDE_CODE_SUBAGENT_MODEL` does not stop that.
- A `PreToolUse` hook given through `--settings` rewrites such a call (`updatedInput`) and denies one, with permissions bypassed. `scripts/hooks/agent-guard` is that hook.
- A shell command the Bash tool started shows in `ps` as a child of the `claude` process: `/bin/zsh -c source ~/.claude/shell-snapshots/snapshot-zsh-<n>-<id>.sh … && eval '<command>'`, in the foreground or the background. (mini)
- A sub-agent's transcript is `~/.claude/projects/<project>/<session>/subagents/agent-<id>.jsonl`. (mini)
- `cursor-agent` 2026.10.01 on the mini has `--resume [chatId]` and `create-chat`; its chats are under `~/.config/cursor/chats/<md5 of cwd>/<chat id>/` and hold requests, tool calls and shell timings, and no token counts. Resuming a Cursor builder for its fix is not built.

**How a failed read is reported.** A reader's first non-blank line on stderr is the reason (each of `hl-read-secret`'s starts `hl-read-secret: `), and that is what the keeper logs, what a failed read answers (``the reader did not give `<name>` (<ref>): <reason>``) and what a worker's `hl-env FAILED` line carries; a value it printed before failing is withheld. The kit reads nothing else from it. (An earlier version looked in the author's own reader's stderr for a line saying it had fallen back from a self-hosted secrets server to the rate-limited service account; that host-specific parsing is gone.)
