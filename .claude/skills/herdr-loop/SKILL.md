# Herdr loop

**The author's loop system since 2026-10-15.** It grew out of LoopRunner, an earlier headless loop runner, and replaced it and the author's older shell-driven loops; LoopRunner was shut down on 2026-10-15. It keeps LoopRunner's backlog format and its merge lock (`refs/looprunner/merge-lock`), so the two could run side by side while they were compared.

One manager agent, in a tab of a Herdr workspace on an always-on Mac (the author's is a Mac mini, reached from a laptop over SSH), works a backlog by driving interactive Claude Code and Cursor sessions in other workspaces: one workspace for each piece of work, named for it, with the agents that run at the same time as tabs inside. It keeps LoopRunner's protocol (agree what "done" means, build, grade independently, merge on a PASS, confirm the deploy) and drops the runner: no headless wrapper, no container, no GUI. The approved design and its reasons are in `references/design.md`; this file is how to use what exists.

## The parts

- **Manager prompt** (`references/manager-prompt.template.md`): reusable and stateless. Fill its `{{…}}` parameters once per program; the same text restarts the manager at any time, because where things stand is in the ledger.
- **Briefs** (`references/briefs/`): what a worker is told. One brief per worker per attempt, filled by `hl-spawn` from the item's record, its route, the program's settings and the repository's facts; see `briefs/README.md`.
- **Scripts** (`scripts/`): the lines a model must not hold alone, and the plumbing a model gets wrong when it types it by hand.
  - `hl-items` counts attempts and refuses a phase past its bound. It records the manager's route for an item and refuses one below the item's floor. `verify-line` loads a Verify line the operator corrected in the backlog file after the run began; it is the one edit a running run's files take. `exempt` records, with the manager's reason and only when typed in the shell of the session holding the program's claim, that one item may change one file its repository's spec protects and lets be exempted (`exemptable`); `hl-merge` reads that record, at the check after a build and at the merge, and nothing wider.
  - `hl-flow` runs the sequences that never vary, one command each: `prepare` (worktree, branch, port, contract, the repository's setup), `built` (the check after a build, then close the builder or send the build back), `review` (serve the build and start its reviewer), `reviewed` (stop the build, close the reviewer, read the verdict against the reviewer's transcript, post it), `close`, and `save` (the generated ledger tables, commit, push, heartbeat, and the size of the manager's context).
  - `hl-verify` runs a merged item's Verify line and records what it gave. The item's wait is a deadline, not a soak.
  - `hl-train` is for a repository that runs a train (`train` among its facts in the spec). Its items merge into `hl-train/<program>` on their review. `test` pins that branch's head and opens a batch's pull request into the base, which runs the required checks on it; `promote` merges a green batch into the base under the merge lock; `repair` closes a red one and writes the item that repairs it. Nothing reaches the base but a batch the required checks passed as a whole.
  - `hl-spawn` starts a worker: counts the attempt, opens a tab in the run's workspace, loads its secrets, starts the agent with its role's tools, sends the brief. It gives the attempt back if the worker never came up. Closing a worker also kills what its shells left running, which closing its pane does not (`hl/reap.py`). A worker that ends without a result is closed, voided with `hl-items void` (which sets its files aside under `voided/`) and started again under the same number. `end-run` closes a run's workspace, and only once its work has shipped.
  - `hl-wait` is the manager's one background wait; it reports the next thing worth looking at, once.
  - `hl-serve` runs a build for a grade and proves it is stopped afterwards.
  - `hl-verdict` decides whether a verdict file is usable.
  - `hl/confirm.py` (no command of its own) says whether the review after a rework is a full review or a delta confirm, for a run whose policy is `confirm: delta`. `hl-flow review` reports its answer with the reason and takes `--full`; `hl-merge` asks it again before it merges on a confirm's pass.
  - `hl-merge` is the only way anything merges, and with `--after-build` checks a build before a grade is spent on it. With `--outside <pr>` it merges a pull request from outside the program that a steward labeled `rollout-ready`, where `program.json` says `"outside_prs": "adopt"`; `hl-handoff` lists those and passes one over (`hl/outside.py` says why).
  - `hl-claim` makes sure one manager runs a program, and records the binaries it runs; a binary that updated itself is accepted and recorded, never a reason to stop.
  - `hl-watchdog` starts a program's first manager, and another whenever none is alive.
  - `hl-secrets` keeps the program's secrets. One process per loop root reads the GitHub token, the workers' Claude token and the ntfy password the first time each is asked for, and answers from memory after: the author's 1Password service account allowed 1,000 requests a day, and reading on every call used them up in ten hours. With `"secrets": "keeper"` in `program.json` the scripts that reach GitHub take the token from it, and a worker's pane and the watchdog ask it. `budget` says what a 1Password service account has left, and that it does not apply to any other store. It has not yet run on the mini.
  - `hl-read-secret <ref>` is how the kit reads one secret, unless `program.json` names another reader in `secrets_reader`: `file:<path>` (a file only you can read; it works everywhere, so it is the default), `op://…` (the 1Password CLI), `keychain:<service>` (the login keychain: in panes and LaunchAgents, not over SSH) and `env:<NAME>`. It prints the value and nothing else, or one line on stderr and exits 1. `references/host-facts.md`, "Reading a secret", has the rules.
  - `stage.sh` and `hl-stage` put a program on the loop host from one spec file: the kit at one commit, the clones, the settings, the filled prompt, the ledger and the first runs.
  Which engine builds and at what effort, whether an item's premise needs an independent check, whether it changes something a person looks at, and what a failure means stay the manager's judgement, and are meant to be.
- **Ops card** (`references/ops-card.md`): the manager's commands and what each answer means. It wins over the prompt where they disagree about a command. `troubles.md` is read by entry when something goes wrong; `host-facts.md` is for whoever changes the kit or sets a program up.
- **Authoring guide** (`references/authoring.md`): how to write items and a spec for this loop: Accept lists that hold behaviour, floors, item size, and a repository's facts said once in the spec.

Run the tests from `scripts/`:

```
python3 -m unittest discover -s tests -t .
LOOPRUNNER_SRC=<a LoopRunner checkout> python3 -m unittest discover -s tests -t .   # adds the lock compatibility tests, where you have one
```

## Running a set of backlogs

This is done from the laptop (any machine with SSH to the loop host and a checkout of your control repository), by whoever is asked to run the backlogs. The operator has said to drive Herdr on the loop host as needed for this (2026-10-11): nothing below waits on them.

Your control repository is a private repository of your own that holds this kit at `.claude/skills/herdr-loop/`, each program's spec and backlog files under `programs/<name>/`, and, on each program's own branch, its ledger. Ledgers hold private detail (what was built, decided and found), so keep that repository private.

0. **Once per host.** See that the host has what `references/host-facts.md`, "What a loop host needs", lists: Herdr, at least one Claude seat signed in (`~/.claude-seat-a`, `~/.claude-seat-b`: in a pane on the host, `CLAUDE_CONFIG_DIR=~/.claude-seat-a claude`, then `/login`) with the seat recorder in the shared `statusline.sh`, the Cursor CLI if Cursor is to build, and the loop's GitHub token where `hl-read-secret` can read it over SSH: a file only you can read, such as `~/.config/herdr-loop/gh-token` (mode 600), which is the template's `gh_token_ref`. Copy `scripts/hl-read-secret` to `~/.local/bin` on the host: `stage.sh` arrives over SSH with nothing beside it, and looks for the reader at `HL_READ_SECRET`, then beside itself, then on `PATH` (`~/.local/bin` first). Install the evaluator's browser (below).
1. **Write the spec.** Read `references/authoring.md` first if you are also writing the items. Copy `references/program.spec.template.json` to `programs/<name>/program.spec.json` in your control repository, beside the program's backlog files, and fill it in. Its `repos` block says what is true of each target repository, once: what its required checks run, the command that makes a checkout ready, the paths a person sees, the paths no item may change, and what every worker there should be told. It names the program, its loop root (`/Users/<you>/loops/<program>`: an absolute path, and never inside a checkout that something else syncs, reverts or cleans), the target repository, and the streams. A stream is a part of the work that can go on beside the others, from its own clone: say which paths it may write and how an item's port is worked out, and give its first run a `work` name. That name is the label of the run's workspace in Herdr, so say what the run completes ("Help desk portal"), not an id. The four `prompt` values are prose only you can write: the files in order with the gates between them, what is production, the capacity rule, and who shares the workers' account. Commit and push it with the backlog files. `programs/example/` holds a filled example.
2. **Stage it on the loop host:**

   ```
   ssh <you>@<loop-host> 'HL_GH_TOKEN_REF=file:~/.config/herdr-loop/gh-token zsh -s -- <owner>/<control-repo> main programs/<name>/program.spec.json' < .claude/skills/herdr-loop/scripts/stage.sh
   ```

   The arguments are your control repository, the branch that holds the kit and the spec, and the spec's path in it. `HL_GH_TOKEN_REF` is required: the reference `hl-read-secret` reads the GitHub token from to read and clone the control repository. Over SSH the login keychain is locked, so a `keychain:` reference does not work here; a `file:` one does, and an `op://` one where `op` is signed in without the desktop app (a service account, say). It clones your control repository to `<root>/ledger` on the program's own branch, installs the kit from that clone at one commit, writes `program.json`, makes one clone of the target per stream with the hook that refuses a commit naming a tool, fills the manager prompt, starts the ledger, initialises each stream's first run, and runs the installed kit's tests. It prints what it made. Running it again installs a newer kit and rewrites the prompt, and leaves the ledger, the runs and the worktrees alone; do that between items. It may be run from another branch than the first time (from `main`, once the program's own branch has been merged): the program's branch is brought up to the one being staged, which wins wherever the two disagree, and the kit is taken from it file for file. If that cannot be done it says so and leaves the ledger clone as it was.
3. **Start the manager:**

   ```
   ssh <you>@<loop-host> '<root>/.claude/skills/herdr-loop/scripts/hl-watchdog --root <root> --herdr <path to herdr on the host> start --note "first start"'
   ```

   It opens a workspace labeled with the program's name, starts the manager in it, and answers `"action": "started"` once the manager has taken its prompt. If it refuses with "did not take its prompt", it has closed that session: run it again. The manager claims the program, pins the binaries, and from there works the backlog: one workspace per run, named for its work, closed when that work has shipped.
4. **Install the watchdog**, once the manager has pinned the binaries (a minute after it starts): `ssh <you>@<loop-host> '<root>/.claude/skills/herdr-loop/scripts/install-watchdog.sh <root>'`. A LaunchAgent, labeled `local.herdr-loop.watchdog.<program>` (set `HL_LAUNCHD_PREFIX` for a prefix of your own, and set it the same for `--remove`), looks every five minutes and starts a manager when none is alive. It starts disarmed; the manager arms it. It is a change to the host: note it wherever you keep track of the host, and remove it (`install-watchdog.sh --remove <root>`) when the program is complete.
5. **Watch it** in Herdr (`herdr --remote <you>@<loop-host>`), and read the ledger (`LEDGER.md` in the program's folder, on the program's branch) for where things stand. To say something to the manager: `herdr agent prompt <its pane> "<one short line>"`; anything longer goes in a file it is pointed at.

A program's manager and Claude workers run on one of its Claude seats, never on the host's default sign-in (the operator's own). `claude_config_dir` in the spec's settings names the seat it starts on and `claude_seats` the others it may move to (each a `~/.claude-<name>` beside `~/.claude`, signed in, sharing the default's `settings.json`, hooks, plugins and skills; `references/host-facts.md`, Claude sign-ins); the template lists `~/.claude-seat-a` and `~/.claude-seat-b`, so a spec needs only `claude_config_dir`. The watchdog decides which seat the program runs on, so several programs can share the seats side by side: it keeps the program on a seat with room in both usage windows (under `seat_full_percent`), places it on another seat with room when its own fills, and pauses it while no seat has room; `scripts/hl-seat --root <root> status` shows the readings. Staging refuses a program with no seat and a seat with no sign-in. A restaged setting reaches each worker at its next start and the manager at its next start or hand-over.

On a new host, or after changing the pin in `references/mcp-playwright.json`, install the evaluator's browser once: `npx --yes @playwright/mcp@0.0.82 install-browser chrome-for-testing`.

Backlog files keep the format LoopRunner reads (`## <ID> — title`, `**Scope.**`, `**Accept.**`, `**Depends.**`, `**Verify.**`), so files written for it run unchanged. `Depends` may name an item in another file of the same run.

## Decisions on record

These came from the operator. Do not "correct" them. Each carries its date; where a later one replaces an earlier one, both are shown.

The earlier behaviour is `premise: always` in `program.json`. A loose item still gets a drafted and reviewed contract, and an evaluator's amended contract still binds as written (2026-10-11).
- **2026-10-11, standing:** the manager picks the builder; Claude always evaluates. **2026-10-12, added:** the manager decides which model and when. **2026-10-14, superseding the cheaper-first default (measured in the first production program):** Sonnet builds every item that creates or changes product behaviour or anything a person sees; Cursor builds only a clearly mechanical item (a constant, a rename or move, a version bump, a verbatim string, a named deletion), and a Cursor build that fails one review is rebuilt on Sonnet. Sonnet reviews.
- **2026-10-12:** how an item is checked follows what it changes. Work a person looks at keeps pixel-level checking; backend work does not need the full frontend testing every time. The manager tells them apart and routes.
- **2026-10-12:** full suites are not run at every step. They run once, late: the repository's required checks, held green at the merge.
- **2026-10-12, later the same day, going further than the line above:** the full suites are not run for every pull request. "Sonnet checks it at least one time and provides feedback to a new, fresh Compose 2.5 to fix that. That is merged, checked in, and pushed, and we do testing more after the fact. We launch test cases while other work is going on." Tests run on batches ("If there are 40, maybe you let 5 of them go, or 5 key PR check-ins, before you do the full test suite"), their failures go back to the manager as fixes to schedule, and "there may be reasons to slow that train down or do more frequent testing, but that has to be done at the manager level." **How it was built, and where it differs from those words:** an item merges into an integration branch per repository (the train), not into the base, and a batch the required checks passed is promoted to the base. On the mobile app backend's repository a push to `main` runs a Terraform apply and `main` requires the checks on GitHub, which the loop's token cannot bypass by design; untested merges on a base itself would need its protection changed, and that is the operator's to ask for. It is a setting per repository (`train` in the spec). **The fix itself (built 2026-10-13):** with `confirm: delta` in `program.json`, a fix that follows a failed review is checked by a fresh Sonnet session against that review's fix list and the change made since, in place of a second full review. It is never merged unreviewed, and a fix that is large, holds a merge, or reaches a page nobody looked at still gets the full review. `confirm: full`, the default, is the behaviour before this.

## Rules for anyone changing the kit

- A script may refuse; it may not decide. If a change puts judgement into code, it belongs in the prompt as guidance instead.
- A gate that is loosened needs a test that shows the case it now allows, and the reason in the commit message.
- Never test the lock on a real repository's `refs/looprunner/merge-lock`. The tests use local bare repositories.
- Briefs and the manager prompt are read cold by a model with nothing else to go on. Say what is to be done and why in plain sentences; avoid a rule without its reason.
- A rule leaves a brief only when a script holds it. Say in `references/briefs/README.md` which script, or list the removal there as unproven.
- A new behaviour gets a setting in `program.json` whose absence means the kit's earlier behaviour, and a run keeps the policy it was created with. A program that is live is never changed by a kit merge.
  - The one exception is a check that decides nothing a run's policy decides: a refusal moved earlier, to where the same failure is already certain (a look with no port refused at the route, not at `built`); a fact added to an answer (a conflicting pull request reported, a criterion's missing tool); or a verdict's shape accepted where no script or step acts on the field (a `criterion` finding with no number). Such a change needs no setting, and its commit says which of these it is and why. One that loosens a gate still needs its test and reason (above). Anything that lets more through to a merge, or changes how an item is built, reviewed or merged, gets its setting.
- Before a change to `hl-merge` or `hl-watchdog` is accepted, have it reviewed by a fresh session that is given the code and not your conclusion. Both of round 2's reviews found faults the tests and a mutation pass had not.
